# Review r5 (Codex, 2026-10-17) — VERDICT: CHANGES

Reviewed the r4 fixes. Output: docs/reviews/review-r5.out.md. PoCs: docs/reviews/r5-poc.t.sol.txt.

| # | Severity | Finding |
|---|---|---|
| 1 | high | a late but accepted Core → EVM credit becomes unaccounted (retry without raising `expectU`; `SETTLE_DELAY` closing while a credit is in flight) |
| 2 | medium | a second order overwrites the spend lock of a still-pending first one |
| 3 | medium | anyone can drain the USDC float to the EVM, so buys cannot run |
| 4 | high | the 1-hour `SPEND_LOCK` / `SETTLE_DELAY` are guesses, not documented bounds; if wrong, value is lost, not only paused |

## What changed
Not five more patches. Every round so far found a hole in the same place: books the contract
kept itself (`rH`/`rU`, expected arrivals, stages, locks, timeouts) and tried to reconcile with
what Core did, while the EVM gets no signal from Core. The pool was rebuilt with **no books**:
reserves are actual EVM balances plus actual Core balances, read every time (docs/design.md).

| # | Status |
|---|---|
| 1 | gone: nothing is "expected"; a late credit is counted when it lands (`test_lateCreditCountedWhenItLands`), a rejected send leaves its tokens on Core, counted (`test_rejectedSendLosesNothing`) |
| 2 | gone: no locks; an order that spends a balance first only makes a later send fail, which loses nothing |
| 3 | fixed: `floatFloor`, below which only the keeper may move Core USDC (`test_floatFloor`) |
| 4 | gone: no time bounds. The remaining assumption is Hyperliquid's documented block ordering for transfers, covered by `QUIET_BLOCKS` = 2 |

The r5 PoCs target the removed API and no longer compile; they are kept for the record.
